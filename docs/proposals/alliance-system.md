# 联盟系统（城商行联盟定制）方案

2026-10-27 起草（v2，按讨论调整） · 分支 `feat/alliance-system`（长期分支，**不合并 main**）

## 背景与目标

城商行联盟需要一套"作战情报台账"：由各系统的开发人员把业务系统登记成条目（系统名称、URL、安全描述——框架、业务、加解密、平台形态等），**新建任务时直接选这些条目当目标**，让渗透过程带着已知信息测试，并按联盟维度统计资产与覆盖情况。

v2 调整（按讨论）：① **不做"成员单位"表**——单位归属对测试协助没有直接价值，改为系统上的一个选填文本字段；② 描述由**开发人员填写**，表单只列"对渗透真正有用"的项 + 一个"其他"补充项（见 §二）；③ 最终在 `E:\AI\SCCBA` 交付一份**纯源码包**（调试仍在 series 里，见 §七）。

四件事：

1. 联盟资产台账：系统 → 入口，安全描述 + 标签；
2. 新建任务时选择联盟系统作为目标（复用现有"资产 → 任务"链路）；
3. 描述随任务进入渗透流程（分级注入，见 §四）；
4. 联盟资产统计（分布、覆盖、关联任务/漏洞）。

## 一、数据模型（3 张新表，`CREATE TABLE IF NOT EXISTS`，纯加法）

| 表 | 字段（要点） | 说明 |
| --- | --- | --- |
| `alliance_systems` | id, name, url, owner_unit, platform, framework, crypto, business, security_note, tags[], status, created_at, updated_at | `owner_unit` 选填文本（如"某某银行"）；`platform` ∈ {web, 小程序, app, 公众号, 混合} |
| `alliance_endpoints` | id, system_id, url, host, port, scheme, note, asset_id | 系统 1—N 个入口；`asset_id` 关联标准资产库（可空，选择任务时回填） |
| `alliance_task_links` | task_id, system_id, created_at | 任务 ↔ 系统，供"被测覆盖率 / 漏洞数"统计 |

独立建表而不是塞进 `assets.extra`：

- 联盟条目是**人工写的情报**（含加密方式、业务背景、对接说明），标准资产库是**扫描事实**——生命周期、更新方式、可见性都不同；
- 新表对上游同步零冲突；`extra` 已被现有工具按分组字段使用，上游改语义就会打乱。

## 二、开发人员填写表（交给开发填的字段清单）

原则：**只问对渗透有用的**；每项 1–2 句话即可，不会的填「不清楚」比留空好；表单里每项都带示例占位符。

**必填（4 项）**

| 字段 | 说明 / 示例 |
| --- | --- |
| 1. 系统名称 | 例：信贷管理系统、电池溯源平台 |
| 2. 访问地址 | 主入口 URL，多个用换行分隔；有测试环境请标注 |
| 3. 系统形态 | Web / 小程序 / APP / 公众号 / 混合（可多选） |
| 4. 业务功能 | 一两句话：给谁用、干什么。例："客户经理提交贷款申请，支行/总行分级审批，对接核心系统放款" |

**建议填（选填，3 项）**

| 字段 | 说明 / 示例 |
| --- | --- |
| 5. 技术框架 | 例：Java Spring Boot + Vue（JeecgBoot）、PHP ThinkPHP、.NET；不确定写"不清楚" |
| 6. 登录与加解密 | 例：账号密码登录；前端 RSA 加密口令；接口 token 放 header；短信验证码登录 |
| 7. 中间件/组件 | 例：Nginx + MySQL + Redis + Nacos / MinIO |

**最后一项（8. 其他）**：任意补充——测试注意事项（如"生产数据，禁止删除/修改"）、历史问题、对接人联系方式、特殊约定等。

> 表单提示文案建议：*本说明用于渗透测试时了解系统背景，不会影响系统运行；不清楚的项填"不清楚"即可。*

DB 映射：4→`business`、5→`framework`、6→`crypto`、7 与 8→`security_note`。

## 三、UI 与接口

- 新页面 `/function/alliance`：台账 tab（按平台 / 标签 / 关键词 / 所属单位筛选，CRUD，"从标准资产库导入"）+ 统计 tab。
- 导航加一项「联盟系统」，**由设置开关控制**（默认关闭），不影响非联盟环境。
- API（新文件 `server/alliance.go`）：`/api/alliance/systems`、`/endpoints`、`/stats`。
- 新建任务页（`web/src/components/tasks/task-creation-form.tsx`）加选择器「联盟系统」，选中后：
  1. 把系统入口解析成标准资产（存在即复用，不存在按现有插入路径登记）；
  2. 走现有 `AssetIDs` 链路 → 自动进 `task_scope`、自动批准（沿用"任务创建时直接选择"规则；审批模板仍可控）；
  3. 生成目标简报写入任务描述（见 §四）。

## 四、描述怎么"带着进任务"（分两级，控制 token）

- **第一级 · 目标简报（一次性、有界）**：选中系统压缩成一段文本写进任务 `description`，格式 `系统名 | 入口URL | 一句话（框架/平台/业务）`；预算：每个系统 ≤3 行、最多 10 个系统、总长 ≤1500 字，超出只列名字。注意：任务目标会进入 planner 提示并**每轮计价**（`agent/planner.go` 的「原始任务目标」），必须短。
- **第二级 · 按需详情**：完整安全描述随任务起点保存（origin fact 附加字段或首个 digest 节点），测试中经 `context_search/context_get` 按需读取，不进每轮提示。
- **（二阶段可选）Host 情报注记**：该系统 host 被 worker 锚定时，注入一条 ≤300 字联盟情报（框架/加密/业务），复用现有 `HostPinnedNote`/`host_lessons.go` 的挂载模式，让"带着描述测试"不额外花一次调用。

## 五、统计

复用三张表 + 现有 tasks/findings：系统数、入口数；平台分布、框架分布、加解密方式分布；标签 TOP；**被测覆盖率**（有 `alliance_task_links` 的系统占比）、关联任务数、按严重度的漏洞数。全部只读聚合。
