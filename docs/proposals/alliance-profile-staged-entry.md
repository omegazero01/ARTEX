## 3. 设计原则

1. **软门槛，不硬拦。** 不强制画像必选、不要求填满上一阶段才能进下一阶段、不因为字段未知阻止保存；这是已经拍板的产品方向。
2. **版本不可变。** 保存只追加新版本，不覆盖旧版本；任务快照永远不变。
3. **AI 只建议，人写入。** AI 没有直接改正式画像的工具；接受建议必须由人点击。
4. **不制造“假完整”。** 只有“已提供/人工确认且有内容”或“不适用且有原因”才算已填；`unknown` 无论有没有说明文字，都不算已填。
5. **不做数据库迁移。** A、B 只改前端和少量保存逻辑；C 是验证加一个字段修复；D 是数据操作。现有表结构、JSON 结构、API 路径都不变。

## 4. 改动 A：未知字段留空，不写“未提供”

### 4.1 问题

现在九号画像 34 项全部非空，但 20 项是 `unknown`。原因是早期为了“说明情况”，把“未提供/未验证”写进了 `value`。这会造成：

- 界面上看起来像填满了；
- 用户不知道哪些是真的有资料；
- AI 可能把“未提供”当成一条背景资料；
- 违背手册“未知就写未知、不要用猜测填满”的原则。

### 4.2 规则

新增“有效已填”口径（只在前端统计和展示层使用，不修改数据库字段）：

```text
有效已填（counted）=
  (status == supplied || status == confirmed) && value.trim() != ""
  或
  (status == not_applicable && value.trim() != "")

待确认说明（pending note）=
  status == unknown && value.trim() != ""

未填（empty）=
  status == unknown && value.trim() == ""
```

- `unknown` 默认留空。
- 如果确实需要写一句“为什么还不知道”，以 `待确认：` 开头，例如“待确认：未取得测试授权”。
- `待确认说明` 在界面上用黄色标签显示，不计入“已填”。
- `not_applicable` 必须写原因才算完成；只选“不适用”但不写原因，显示“缺原因”，不计入已填。
- 不自动清空用户已经写的文字，避免误删；只给提示和统计。

### 4.3 界面

1. 字段输入框 placeholder 改为：`未知请留空；需要说明时以「待确认：」开头`。
2. 字段标题右侧显示状态；当 `unknown` 且 `value` 非空时，显示小黄条：`待确认说明，不计入已填`。
3. 阶段标签显示：`1. 首轮接入 · 已填 5/8 · 待确认 2`。
4. 顶部总览显示：`有效已填 14/34 · 待确认 2 · 未填 18`。
5. 保存时如果存在 `not_applicable` 但原因为空，前端提示“请补不适用原因”，但不阻止保存（软提醒）。

### 4.4 兼容性

- 数据库字段不变；旧画像里的“未提供”文字不会被自动删除。
- 统计口径变化只影响界面显示；API 返回值不变。
- 旧画像打开后，用户可手工清空 `unknown` 字段；九号那份由 D 统一清理。

### 4.5 测试

| 用例 | 步骤 | 期望 |
|---|---|---|
| A1 | 新建画像，不改任何字段 | 有效已填 0/34；阶段 1 为 0/8 |
| A2 | 阶段 1 填一个 `supplied` 且有内容 | 阶段 1 变为 1/8；总数 +1 |
| A3 | 某字段填“未提供”，状态 `unknown` | 显示“待确认说明”；有效已填不增加 |
| A4 | 某字段填“待确认：未授权”，状态 `unknown` | 显示待确认；有效已填不增加 |
| A5 | 某字段选 `not_applicable` 但不写原因 | 显示“缺原因”；有效已填不增加 |
| A6 | 某字段选 `not_applicable` 并写原因 | 计入已填 |
| A7 | 已有旧画像打开 | 不丢内容；统计按新口径重新计算 |

### 4.6 验收标准

- 九号之外的任意画像，`unknown` 字段留空时不会被计入“已填”。
- 界面上能区分“有效已填 / 待确认说明 / 未填”。
- 保存、版本、API 行为不变。

## 5. 改动 B：新建后默认首轮接入，提供“保存首版”引导

### 5.1 目标流程

```text
新建画像（第 1 步：基本信息）
  → 保存
  → 自动打开画像编辑器，默认 phase=1
  → 顶部提示：先填首轮接入，未知留空，保存首版
  → 用户填 S1 已知项
  → 点「保存首版（v2）」
  → toast：首版已保存，后续可继续补充
  → 以后从列表点「继续补充」，打开第一个未完成阶段
```

### 5.2 版本语义（重要）

当前创建系统时就写了 `version=1` 的自动初稿和一条 revision。所以：

- **v1 = 自动初稿**，由第 1 步基本信息映射而来（S1-01 名称/环境、S1-03 归属单位、S1-04 业务、S1-08 框架、S2-04 安全备注、S2-12 加解密），可能已经有内容，但不是人工整理过的首版；
- **第一次人工整理保存 = v2 = 首版**；
- 后续每补充一次，v3、v4……

不在本次改 `version=0` 或删除 v1，因为那会影响已有 `alliance_task_snapshots.profile_version`、revision 主键和现有数据。界面上明确标注即可：

- 版本历史：`v1 自动初稿`、`v2 首版`、`v3 手工补充`、`v4 反哺接受`（来源文案可后续做，本次至少标出 v1/v2）。
- 保存按钮：
  - `version == 1`：`保存首版（v2）`
  - `version > 1`：`保存修改（v{version+1}）`

### 5.3 界面改动

1. 编辑器顶部增加说明卡：

   > 建议先填「首轮接入」并保存首版；深入测试、持续完善可以以后补。
   > 不确定的字段请留空，需要说明时写「待确认：…」。保存不会影响已绑定任务的旧快照。

2. 阶段 Tab 标签增加完成度（见 A 的口径）。
3. 默认 `phase=1`（当前已经是 `useState("1")`，保持不变）。
4. 第一阶段为空时，显示：`本阶段还没有内容。可以先填系统名称、入口、联系人、测试边界，再保存首版。`
5. 保存后：
   - 首次保存：`首版已保存（v2），后续可随时补充`；
   - 后续保存：`已保存（v{newVersion}）`。
6. 列表行增加「继续补充」按钮：
   - 打开画像编辑器；
   - 自动切到第一个“有效已填 < 字段总数”的阶段；
   - 不改变任何数据，只是导航。

### 5.4 保存按钮的防误触

- 增加 `dirty` 状态：文档和环境与加载时相同，则保存按钮禁用，提示“没有修改”。
- 后端 `SaveAllianceProfile` 增加幂等判断：
  - 将当前文档和环境规范化后比较；
  - 完全相同则直接返回当前 profile，不新增 revision、不涨版本；
  - 这符合手册“完全相同的内容重复保存通常不会生成新版本”，也避免版本噪音。
- 该判断只影响保存接口；任务快照、审核接受路径不变。

### 5.5 不做的事

- 不做“必须填满 S1 才能保存”的硬门槛；
- 不做“不填 S1 不能创建任务”的硬拦截；
- 不改数据库版本号规则；
- 不把 34 个字段拆成 34 个步骤（太重）。

### 5.6 测试

| 用例 | 步骤 | 期望 |
|---|---|---|
| B1 | 新建画像并保存基本信息 | 自动打开编辑器，停在阶段 1 |
| B2 | 只填 S1 的两个字段，点保存 | 生成 v2；toast 显示“首版已保存” |
| B3 | 再次打开，未改内容点保存 | 按钮禁用或提示没有修改；版本不变 |
| B4 | 修改一个字段再保存 | 生成 v3；v2 仍可查 |
| B5 | 点列表「继续补充」 | 打开编辑器，停在第一个未完成阶段 |
| B6 | 只填名称/环境就保存 | 允许保存，但提示“首版内容较少，AI 可能缺少背景” |
| B7 | 旧画像打开 | 默认阶段、统计、保存行为正常 |

### 5.7 验收标准

- 新建后不会一上来就看到“34 项都要填”的压力。
- 第一次保存有明确的“首版”概念（v2），后续补充形成新版本。
- 没有修改时不会无意义涨版本。
- 不影响任务快照和既有画像。

## 6. 改动 C：配置真实模型，跑通反哺链路

### 6.1 当前阻塞

- 容器日志：`no LLM provider configured`；
- 没有真实任务绑定画像；
- 没有 confirmed 证据；
- 因此“AI 整理建议 → 人审核”从未真正执行过，只能确认代码存在、编译通过。

### 6.2 验证目标

证明下面这条链路真实可用，而不只是代码存在：

```text
任务绑定画像快照
  → 任务完成/失败/超时并收尾
  → 后台发现反哺 run
  → 只读取本任务 confirmed fact/finding
  → 模型输出建议
  → 建议引用证据 ID
  → 人在 UI 看证据、编辑、接受
  → 正式画像版本 +1
  → 任务快照保持不变
```

### 6.3 测试环境

优先使用隔离环境，避免污染现有画像：

- 单独 compose 项目：`sccba-profile-e2e`；
- 独立 PostgreSQL 数据卷；
- 独立端口（例如 8892/8893）；
- 测试目标：本机临时 HTTP 服务（例如 `127.0.0.1:18080`），只包含一个可被发现的测试事实；
- 模型：优先本地 OpenAI 兼容 stub 返回固定 JSON，验证管道；再用真实模型跑一次小任务，验证真实输出。

禁止使用九号官网或任何未授权公网目标做联调。

### 6.4 前置修复（必须）

`ReviewAllianceSuggestion` 接受建议写 revision 时 `environment` 传空串（`db/alliance_profile.go:738-749`）。联调前修掉：

- 读取该系统当前的 `environment`；
- 写入 revision 时带上；
- 验收断言：接受建议后的 revision.environment 与系统一致。

### 6.5 测试矩阵

| 编号 | 场景 | 操作 | 期望 |
|---|---|---|---|
| C1 | 任务未选画像 | 创建任务不选画像 | 无快照、无反哺 run |
| C2 | 任务暂停 | 暂停任务 | 不触发反哺 |
| C3 | 完成但无 confirmed 证据 | 任务完成，无 fact/finding | run=done，建议 0 条，画像版本不变 |
| C4 | 有 confirmed 证据 | 任务完成，产生 1 条 confirmed fact | 生成建议，evidence_ids 非空 |
| C5 | 接受建议 | 在 UI 编辑后接受 | 画像版本 +1；字段值更新；revision.source 为 feedback；任务快照不变 |
| C6 | 拒绝建议 | 拒绝 | 建议 rejected；画像版本不变 |
| C7 | 版本冲突 | 审核时 expected_version 过期 | 409；不写入；提示刷新 |
| C8 | 归档画像 | 归档后接受 | 拒绝；版本不变 |
| C9 | 整理失败重试 | 模拟失败后点“重新整理” | 新 run 产生；旧失败记录保留 |
| C10 | 证据归属 | 构造其他任务的证据 | 建议不得引用其他任务证据 |

### 6.6 证据采集

每个用例至少保留：

1. UI 截图或操作步骤；
2. 接口响应 JSON（任务画像、反哺 run、建议、审核）；
3. 数据库断言：

```sql
-- 反哺 run
SELECT id, task_id, state, error, attempt FROM alliance_profile_feedback_runs WHERE task_id = ...;
-- 建议与证据
SELECT id, system_id, state, suggestion->>'field_id', suggestion->'evidence_ids'
FROM alliance_profile_suggestions WHERE task_id = ...;
-- 版本与来源
SELECT version, source, environment FROM alliance_profile_revisions WHERE system_id = ... ORDER BY version;
-- 快照是否不变
SELECT snapshot FROM alliance_task_snapshots WHERE task_id = ...;
```

4. 任务前后快照哈希对比，证明旧任务不受正式画像更新影响。

### 6.7 通过标准

- C1–C10 全部通过；
- 至少一次真实模型小任务跑通（不只是 stub）；
- 没有任何“AI 直接写正式画像”的路径；
- 接受建议后的 revision.environment 正确；
- 任务快照在正式画像更新前后完全一致。

### 6.8 风险

- 真实模型输出 JSON 不合法：反馈会失败，需检查 prompt 和容错；
- 零 confirmed 证据：这是正常结果，不应当成 bug；
- 模型费用：用小任务、短证据、限量；
- 测试目标必须本地/授权，不能用公网真实站点。

## 11. 风险与开放问题

1. **v1 是空白模板，首版是 v2**，用户可能觉得版本号奇怪。缓解：界面明确标“v1 空白模板 / v2 首版”；不改成 v0 是为了避免影响已有快照和 revision。

3. **`not_applicable` 是否强制写原因**：本文只做软提醒，不硬拦；后续可考虑服务端校验。
4. **真实模型可用性**：没有模型就无法完成 C；需要用户提供可用模型或本地 stub。
5. **附件/文档解析**：不在本文范围；如果要做，需要另立方案（存储、解析、注入边界）。
6. **任务创建时是否提示画像不完整**：本文不做硬拦；可作为后续 P1 的软提醒。
