# 移植工作规则（用户指定的硬约束）

本文件是 `PORTING.md` / `PORTING-AUDIT.md` 的配套规则，优先级高于我自己的判断。
一旦与本文件冲突，以本文件为准。

## 1. 每次修改必须完整展示两边代码

任何一次移植/修改，回复里必须包含三段，且**不省略、不摘要、不用“详见某文件”代替**：

1. **原始提交的完整改动**：`git show <hash>` 的完整 diff（含文件头、上下文行、所有 hunk）。
   提交涉及的文档/CHANGELOG 也要列出，不能只挑代码文件。
2. **本次改动的完整代码**：新增文件给全文；修改文件给完整的新内容（或该文件的完整 diff，逐 hunk）。
3. **逐文件对照表**：原提交文件 → ARTEX 落地文件 → 状态（1:1 / 等价 / 不适用 / 未搬）。

大提交（如 3000 行以上）按文件分段展示，可以分多条消息，但**不允许丢段**。

## 2. 不允许静默削减

- 只要原提交里存在“有落点但没搬”的部分，必须在动工前说明，由用户决定是否接受。
- 用户未点头前，不允许把“部分完成”记成“已完成”。
- 提交标题里出现“移植”二字，即代表行为等价；否则标题必须写明“部分”。

## 3. 验收标准

**“完成”的定义：五处都点到，缺一处就是未完成**

功能不是“源文件搬完 + 单测通过”就算完。任何一个功能都必须逐处核对，并在 `PORTING.md` 里写明每一处的状态：

| # | 层面 | 要核对什么 |
|---|---|---|
| 1 | 数据库 | 表/索引/列是否建齐；老库升级是否兼容 |
| 2 | 后端 API | 写入口、读入口、聚合口径、权限 |
| 3 | 前端可见 | 用户在哪一屏能看到这个能力；类型定义是否补齐 |
| 4 | 归档/导出 | 任务归档、恢复、导出包里是否带上这批数据；旧包兼容 |
| 5 | 测试 | 单测 + 真实环境验证（真库/真进程/真调用），并记录实测输出 |

- 任何一处没做，必须在 `PORTING.md` 第五节写一行“缺什么 / 影响 / 补齐代价”，**不允许只写在 commit message 里**。
- 反过来，`PORTING.md` 第五节写着缺口的条目，不允许在第一节被标成“完整”。

- 符号级：原提交新增的函数/类型/常量，ARTEX 同名符号覆盖率为 100%，或逐个注明“ARTEX 无宿主”。
- 行为级：换了实现的条目，必须并排贴出两边判定逻辑并说明等价理由。
- 测试级：原提交带的测试能搬就搬；不能搬要说明原因，并补等价测试。
- 以上三条未满足，不得提交。

## 4. 记账

- `PORTING.md`：每条一行，状态只有“完整 / 等价 / 部分（缺口见第五节）”。
- `PORTING-AUDIT.md`：符号级核对表，每次新增移植都要补一行。
